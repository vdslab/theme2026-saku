# 既存の実行経路を維持するリファクタリング設計・コミット計画

## 1. 目的と今回の成果物

既存のアルゴリズムを、短く読みやすい関数、責務ごとのファイル、明確な入出力に整理する。
新しいコードは `src/torus_layout/` に追加し、既存の実行経路と並存させる。
どのコミットをチェックアウトしても、そのコミット直前と同じ既存の実行経路が残ることを必須とする。

この文書を作成する作業は設計文書の追加とローカルコミットまでとする。
以下の実装コミットは、その後にこの設計に沿って実行する作業手順であり、実装済みの一覧ではない。
push は、文書作成時も実装時も行わない。

## 2. 変更範囲と守る条件

### 書き込みを許可する場所

- この設計文書 `documents/torus_layout_refactoring_plan.md`
- 新規パッケージ `src/torus_layout/` 配下だけ

既存の `main.py`、既存の各手法、`src/generator/`、既存テスト、`examples/`、
`experiments/`、`.vscode/settings.json`、ルートの設定・依存管理ファイルは変更しない。
既存ファイルの削除・移動・ラッパーへの差し替えもしない。
ユーザーの作業中の変更をコミットに含めたり、元に戻したりしない。

### 既存経路からの隔離

- 既存コードに `torus_layout` の import を追加しない。
- 新規パッケージの通常実行コードは、旧 `main`、旧アルゴリズム、旧描画モジュールを import しない。
  アルゴリズムは新パッケージ内へ実体を移植して整理する。
- 比較テストから旧実装を参照することは許可する。
- 整理済みの `generator` は利用例・テストのグラフ生成に再利用できるが、変更しない。
  パイプライン本体は生成済みグラフを入力とし、生成器に依存しない。
- 内部 import は相対 import、外部からは `torus_layout.*` を使う。
  `sys.path` の書き換え、既存パッケージ名の横取り、実行時の関数差し替えはしない。
- import 時に求解、画像保存、GUI表示、環境変数の読み込み・設定を開始しない。
  Gurobi環境の生成は、従来どおり実際に求解する時点で行う。
- テストの実行後に作業ディレクトリ、乱数、環境変数などの変更を残さない。

### 挙動を変えない

対象の手法、目的関数、制約、探索範囲、初期値、反復回数、処理順、同点時の選択、
巻き数の計算、重み、座標計算、画像の表示・保存仕様は維持する。
辺の重複・並び順、空レイヤー、入力の受理条件も、便利そうという理由で正規化・変更しない。

型注釈、名前付きの結果、内部関数への分割、共通処理の抽出、既存の処理を呼ぶ新入口は
構造整理として認める。ただし新しい計算、評価指標、探索オプションを追加しない。
公開APIの見せ方を整理しても、旧APIと旧経路はそのまま残す。

前案に含まれていた次の項目は、今回の実装範囲から外す。

- 時間制限・準最適などの扱いを変える、最適性保証のために探索を変えること
- `qp` の丸め方法、丸め後の自動修復、返却時の判定を変えること
- 新しい乱数シード制御や乱数器の独立化
- 新しい計測範囲、評価指標、実験ログの永続化、一括実験機能
- 新しい元辺から分割辺への対応データの生成・保存
- 旧 `main.py` の新パッケージへの移行

既知の問題は説明・再現テストに残す。リファクタの比較で旧実装の問題を見つけても、
新実装だけで暗黙に修正しない。解の妥当性確認は比較テストで行い、旧挙動と矛盾する場合は
既知の問題として区別する。

## 3. 対象と責務

対象は現在の `main.py` が使う計算経路と、そのバランス調整の4手法に限定する。
旧定式化や別の描画方式を全部移植する計画ではない。

| 元の実装 | 新しい配置 | 責務 |
| --- | --- | --- |
| `layer_assignment/torus_binary_search.py` | `layering/search.py` | 現在の二分探索を行う |
| `layer_assignment/torus_two_stage.py` の `minimize_torus_edges` | `layering/minimize_wraps.py` | 固定レイヤー数でトーラス辺数を最小化する |
| `layer_assignment/torus_balance.py` | `layering/balance/` | 4手法を別ファイルに分ける |
| `lib/create_gurobi_env.py` | `layering/lib/solver.py` | 同じ設定でGurobi環境を生成する |
| `lib/insert_dummy_node.py` | `subdivision.py` | ダミー挿入を独立した前処理にする |
| `crossing_reduction/radial.py` の現在使用する経路 | `crossing/` | 初期順序、交差評価、sifting、巻き数・回転を分ける |
| `coordinate_assignment/brandes_koepf.py` | `coordinates/` | BK本体と周期的な座標調整を分ける |
| `drawing/draw_radial_torus.py`、`drawing/tile_image.py` | `drawing/` | 描画準備、Figure作成、保存・表示、タイル処理を分ける |
| `main.py` の工程の呼び出し・計測・表示 | `pipeline.py`、`reporting.py` | 計算の組み立てと表示を分離する |

使用する部分から到達しない旧関数、旧テスト用の `__main__` 処理は、名前だけ合わせて移植しない。
テストで必要な旧補助処理は、通常実行コードへ混ぜない。

たとえば座標計算と描画の単調回帰処理は共有候補だが、まず挙動を比較する。
関数を数行にすること自体を目的にせず、手法の流れを順に読める分割にする。

## 4. データ契約と依存方向

### 最小限の型

新パッケージの境界には型注釈を付け、長い位置依存タプルを名前付きの結果に置き換える。
旧処理で対応している頂点IDの種類を先に調べ、型を付けるためだけに実行時の受理条件を狭めない。
現行の生成器の整数IDを主要な比較対象とし、既存の文字列ID等の利用があれば契約に明記して維持する。

| 型 | 保持する情報 | 注意点 |
| --- | --- | --- |
| `Graph` | `nodes`, `edges` | 入力の順序・重複を保持する。入口で一括のソートや重複除去をしない |
| `LayerSearchResult` | `layer_count`, `torus_count`, `runtime` | 現在の失敗時の `None` を型に含める。成功とみなす条件を変えない |
| `LayerAssignmentResult` | `node_to_layer`, `torus_flags`, `runtime` | 層別一覧は現在の反復順を維持して導出する。両表現を独立に更新しない |
| `SubdividedGraph` | ダミー挿入後の `graph`, `layers`, `torus_flags`, `weights`, 元頂点の情報 | 空レイヤーを勝手に追加・削除しない。ダミー集合は元頂点との差から導出できる |
| `CrossingResult` | `order`, `winding_numbers` | 同じ `SubdividedGraph` の辺・頂点に対応する。頂点や辺を追加しない |
| `CoordinateResult` | `positions`, 計算時に使った周期 | 周期は現在の式で求め、推測や再定義をしない |
| `PipelineResult` | 各工程の既存相当の結果と時間 | 新しい統計や保存処理を追加しない |

表は結果の意味を決めるためのもの。重複する内容をすべての結果へコピーしない。
`dataclass(frozen=True)` を使っても内側の辞書が不変になるわけではないことに注意する。
公開関数の入力を作業用に変更する必要があれば、必要なコンテナだけを複製する。

### 階層と周期

- 探索で求めた `layer_count`、実際の階層辞書のキー、描画の水平・垂直周期を別の意味として扱う。
- 元実装が空レイヤーを省略する箇所と、保持する箇所を比較で確定して維持する。
- 探索のレイヤー数を、後段の `len(layers)` へ機械的に置き換えない。
- `t_val` は `torus_flags`、`psi` は `winding_numbers` として境界で明示する。
  数式を実装する局所変数では短い記号を使ってよい。

### 関数の境界

依存方向は次のようにする。下位工程から `pipeline` を参照しない。

```text
生成済みGraph
  → 階層数探索・階層割当
  → ダミー挿入
  → 交差削減
  → 座標割当
  → 描画

pipeline → 上記の計算工程
reporting → 結果の型
各工程 → models と自分の工程の lib
```

- `assign_layers` は現在の二分探索と指定されたバランス手法を組み立てる。
- バランスの手法名は `Literal["diff", "diff_square", "qp", "barycenter"]` とする。
  手法ごとの入口は同じ引数・戻り値に揃え、型の付いた辞書または明示的な分岐で選ぶ。
  未実装の手法を登録しない。動的なプラグイン登録や抽象基底クラスは導入しない。
- `insert_dummy_nodes` は現在のダミー挿入を独立した工程として実行する。
- `reduce_crossings` はダミー挿入済みグラフを受け取る。旧関数からダミー挿入だけを分離し、
  反復順・初期化・global guard・回転の後処理を維持する。
- `assign_coordinates` は現在のBK系処理を呼ぶ。新しい座標手法の選択機能は付けない。
- Figure作成と出力を分離しても、従来と同じ描画・タイル化・保存・表示を実行する入口を提供する。
  描画内にある座標補完も、見た目が変わらないように移植する。
- `run_pipeline` は生成済みグラフを受け取り、描画前までを実行する。
  関数から返す情報は、現行の各工程が既に計算している結果に限定する。
  バランス手法・roundsなど現在の設定だけを受け取り、新しい実験モードは増やさない。
- 計測には現在の範囲・単位を維持する。ソルバー時間と工程の経過時間の違いはREADMEに明記し、
  リファクタ中に数値の定義を統一し直さない。
- 結果の表示は `reporting` に分離する。既存相当の一連の使い方もREADMEに載せる。

## 5. Pylanceで公開名がUnknownにならないための設計

提示された `assign_coordinates` の診断は、公開名の定義・公開方法・解決先を確認する対象である。
現行の `src/coordinate_assignment` が公開する名前は `assign_torus_brandes_koepf_coordinates` であり、
別の `examples/sugiyama` には `assign_coordinates` が存在する。これらの名前を混同しない。
提示された診断の発生箇所そのものは未特定であり、既存コードの修正まで完了したとは扱わない。

新パッケージでは、次のように通常の定義と明示的な再エクスポートを使う。

```python
# torus_layout/coordinates/api.py
from ..models import CoordinateResult, CrossingResult, SubdividedGraph


def assign_coordinates(
    graph: SubdividedGraph,
    crossing: CrossingResult,
    *,
    min_gap: float = 1.0,
    smooth_iterations: int = 4,
) -> CoordinateResult:
    ...
```

上記は型付きの入口を示す設計例であり、`...` を本体としたまま実装へ配置しない。
実装するコミットでは本体・完全な型注釈・テストを同時に追加する。

```python
# torus_layout/coordinates/__init__.py
from .api import assign_coordinates as assign_coordinates

__all__ = ["assign_coordinates"]
```

利用側は必ず公開している名前から読み込む。

```python
from torus_layout.coordinates import assign_coordinates
```

### 各コミットで守ること

- 通常の `def` と、実在するモジュールからの明示的な import を使う。
  `__all__` に文字列だけを追加して公開したことにしない。
- 関数の定義・再エクスポート・公開importのテストは同一コミットで追加する。
  まだないモジュールを `__init__.py` から参照しない。
- 内部モジュールは `models` や実装モジュールを直接参照し、パッケージの公開入口を経由して循環させない。
- `import *`、`globals()` による登録、モジュール `__getattr__` による動的公開を使わない。
- `TYPE_CHECKING` 内だけに実体のimportを置かない。
- `Any`、無根拠な `cast`、`# type: ignore`、診断の無効化によって問題を隠さない。
- 必要な `__init__.py` を各パッケージに置く。ルートの `__init__.py` は小さく保ち、
  描画やソルバーをまとめて読み込む便利な一括importは追加しない。
- 型検査用の import 例には、関数の import だけでなく、具体的な入力での型付き呼び出しも置く。
  単にimportが通ることと、型が分かることを別々に確認する。

### 検証環境

既存 `.vscode/settings.json` はプロジェクトのPython環境を選択しているが、
`src` の検索パス指定は明示されていない。新パッケージ用の設定はその配下に置き、
既存ワークスペースの設定を変更しない。

- `src/torus_layout/pyrightconfig.json` に、`extraPaths` で親の `src`、
  `venvPath` と `venv` でプロジェクトの `theme2026-saku` 環境を指定する。
  パスは設定ファイルからの相対パスで記述する。
- 通常実装と公開APIの検査はstrictで行う。旧実装との比較だけを行うテストは別の検査対象にし、
  旧ファイルまで型の修正範囲を広げない。
- 第三者ライブラリの型情報が不足する場合は、まず提供されている型情報を確認する。
  必要なら新パッケージ内の外部ライブラリ接続部分に型を集中させ、
  実APIに根拠のある最小限のstub等を用意する。自前の関数の型をUnknownにしない。
- CLIのPyrightとVS CodeのPylanceは別の実行環境である。
  Pylance確認時は新パッケージを別ウィンドウのワークスペースとして開き、設定の適用と
  インタープリタを確認する。元ワークスペースの設定は書き換えない。
- 公開名に対する `reportAttributeAccessIssue`、未解決import、Unknownの診断がないことを確認する。
  Pylanceを実際に確認できなかった場合は、CLIのみ検証したと明記して完全確認扱いにしない。

設計作成時点では、プロジェクト環境に `pytest` と `gurobipy` は存在するが、
`pyright` / `basedpyright` は存在しないことを確認した。実装の最初のコミットの検証前に、
Pyrightを新パッケージ用の検査環境へ用意する。既存実行環境への依存変更は行わない。
Pythonの起動には必ず `./theme2026-saku/bin/python` を使う。
たとえば一時ディレクトリに検査用ツールを配置して `PYTHONPATH` 経由で実行できる。
実装時には使用した検査ツールのバージョンと再現コマンドをREADMEに残す。

## 6. 同等性と安全性の検証

### 比較の基準

1. 実装開始時のHEADと、作業ツリー上の元実装の内容を基準として記録する。
   未コミット変更がある場合はHEADだけでは不十分なので、実ファイルのハッシュも記録する。
2. パス、分岐DAG、単純閉路、複数閉路、固定シードの生成グラフを使う。
3. 通常入力に加え、旧実装が実際に受け付ける空レイヤー・重複辺・失敗ケースを記録する。
4. 工程単位の比較では、旧実装・新実装へ同じ中間入力のコピーを渡す。
5. ソルバーに複数の最適解がある場合は、制約と目的値を比較する。
   上流の別解により後段の交差数が変わることを、交差削減のリファクタ失敗と混同しない。
6. 決定的な処理は順序・巻き数・辺リストまで一致を確認する。
   浮動小数点の座標は計算スケールに合う許容誤差を明示する。
7. 乱数を使う比較では旧・新の開始状態を揃え、テスト終了時に元の状態へ戻す。
   乱数アルゴリズムや消費順をリファクタの都合で変えない。
8. 経過時間自体の一致は要求しない。計測対象が同じことを確認する。

### 工程別の完了条件

| 工程 | 必須確認 |
| --- | --- |
| 階層割当 | 定式化の一致、既存が実行可能解を返すケースの制約・目的値、失敗時の既存相当の振る舞い |
| 二分探索 | 同じ求解結果列を与えた探索順と戻り値、実ソルバーでの小規模ケース |
| ダミー挿入 | 頂点ID、辺順、層一覧、重み、トーラスフラグが旧実装と一致する |
| 交差削減 | 同じダミー挿入済み入力からの順序・巻き数・交差数、global guardの扱いが一致する |
| 座標割当 | 同じ順序・巻き数からの座標と周期が一致する。既存が保証する間隔・順序を維持する |
| 描画 | 同じ入力で通常描画・タイル描画・保存・非表示を確認する。実際の画像を目視する |
| パイプライン | 同じ工程順・引数・時間の定義で実行し、旧経路の小規模ケースと比較する |
| 公開API | 通常importが成功し、Pyrightで型が解決され、実施できる環境ではPylanceでも確認する |

ソルバーを使うテストと使わないテストを分ける。Gurobiの実求解を一度も実施せずに
階層割当の移植完了とはしない。接続・ライセンス等の理由で実行できない場合は、
未検証の内容を明記し、テストを無条件に成功させて完了扱いにしない。
`.env` の秘密値は出力・コピー・コミットしない。

### 既存経路を保護する確認

- 開始時点の既存Pythonファイルと設定ファイルの内容を記録し、各コミット前にハッシュが一致することを確認する。
- ハッシュ比較に加え、許可した場所以外に追加・変更・削除がないことを確認する。
  既存ファイルが同じでも、同名モジュールの追加によるimportの横取りがあり得るため、差分も見る。
- 最初とパイプライン完成時に、同じ小規模・固定シードの引数で旧 `main.py` の非表示実行を確認する。
  各コミットでは旧公開入口のimport確認とファイル保護の確認を行う。
- 旧経路の不具合や、元からある型診断を新パッケージの変更で隠さない。

## 7. 計算量の改善を認める条件

結果を維持して無駄な処理だけを減らせる場合は改善してよい。
ただし構造整理とは別の `perf` コミットにする。以下をすべて満たすことを条件にする。

1. 繰り返し走査・同じ情報の再構築など、無駄な処理をソースで特定する。
2. 改善前後で同じ入力に対する出力と処理順に関わる挙動を比較する。
3. 規模を変えた計測または操作回数で、無駄が減ることを確認する。
4. 乱数の消費順、同点の選択、辺の重複、重み、例外の条件を変えない。
5. 比較できない変更、結果が変わる変更は今回の改善に含めない。

候補は `insert_dummy_node` の「辺ごとに全レイヤーを走査する処理」である。
頂点からレイヤーへの対応を一度構築すれば繰り返し探索を減らせる。
ただし重複所属がある場合の旧実装の選択順なども維持する。
無効入力を新しく拒否することや、任意のソートを入れることを性能改善に混ぜない。

## 8. コミット単位の作業手順

コード、型、公開import、関係するテスト、説明は、それぞれのコミット内で完結させる。
公開名だけ先に追加するコミット、テストを後から直す前提のコミットは作らない。

| 番号 | コミット名 | 作業範囲 | コミット前の必須確認 |
| --- | --- | --- | --- |
| C0 | `docs: define isolated torus layout refactoring plan` | この設計文書のみ追加 | 既存ファイルを変更していないこと、コミット対象がこの文書だけであること |
| C1 | `refactor: establish typed torus layout contracts` | 最小パッケージ、データ型、旧実装の比較ケース、保護確認、型検査設定を追加 | データ変換で情報・順序を失わない、型とimportが解決する、将来の未実装関数を公開していない |
| C2 | `refactor: extract layer search and diff assignment` | 求解環境、トーラス辺数最小化、二分探索、diffを移植。現在の制約・結果取得を維持 | 小規模実求解・探索の比較、失敗の既存相当の扱い、型検査 |
| C3 | `refactor: separate layer balancing methods` | diff_square・qp・barycenterを移植し、4手法の入口を追加。同じと確認できた部分を共通化 | 4手法の比較、既知のqp丸め問題を改変していない、目的関数・初期解が一致する |
| C4 | `refactor: isolate dummy node subdivision` | 元のダミー挿入を独立した型付き関数にする | 元と同じID・辺順・階層・重み・フラグ、境界ケースの比較 |
| C4p（任意） | `perf: index node layers during subdivision` | C4と分けて繰り返し走査を削減する | 出力の一致と操作回数または計測による改善の証拠。証明できなければ省略する |
| C5 | `refactor: separate radial crossing reduction responsibilities` | 現在使うglobal guard付きsiftingと必要な補助処理を移植・分割 | 同じ中間入力の順序・巻き数・交差数、初期化・反復順・回転処理の比較 |
| C6 | `refactor: extract typed coordinate assignment` | BK本体と周期調整を分割。assign_coordinatesを定義・公開 | 座標・周期の比較、間隔・順序の確認、公開importの型検査 |
| C7 | `refactor: separate torus rendering and output` | 描画準備、Figure作成、従来相当の出力、タイル処理を分離 | 通常・タイル画像の目視、保存・非表示・Figureの後処理、公開importの型検査 |
| C8 | `refactor: assemble isolated torus layout pipeline` | 工程の組み立てと既存相当の表示を追加。READMEの利用例・既知の問題を仕上げる | 新旧の小規模全工程比較、途中入力での比較、型検査、新旧の公開import、旧main実行、全保護ファイルの一致 |

各工程のREADME説明は該当コミットで追加し、C8で一括して後付けしない。
最初に実装する範囲は C1〜C2 とし、その比較結果と型設計を確認した上で C3以降へ進む。
これは毎回ユーザー承認を要求する区切りではなく、実装・検証の区切りである。

### 毎回のコミット手順

1. `git status` とステージ済み差分を確認し、今回の変更とユーザーの変更を区別する。
2. 関係する比較テスト、型検査、公開import、既存ファイルの保護確認を行う。
3. 追加するファイルを明示してステージする。`git add .` や `git add -A` は使わない。
4. コミット対象の名前と内容を確認する。他の作業のステージ済み変更を一緒にコミットしない。
   必要な場合は対象パスを指定した `git commit --only` を使う。
5. 一つの完成した作業単位をローカルコミットする。既存コミットのamend、reset、履歴の書き換えはしない。
6. コミット後に対象ファイル一覧と作業ツリーを確認し、コミットID・検証結果・未検証事項を報告する。
7. push、リモートブランチ作成、PR作成は行わない。

検査に失敗した場合は同じ作業単位で原因を直してからコミットする。
外部要因で検証できない場合は、その工程を未検証のまま完成と報告しない。

## 9. 全体の完了条件

- 既存の実行経路と既存ファイルが開始時から変わっていない。
- 新実装は旧計算コードを呼び出すだけのラッパーではなく、独立した実体を持つ。
- 対象の手法・結果・設定値・表示保存仕様を維持している。
- 公開関数は具体的な型と明示的なエクスポートを持ち、未解決importを残していない。
- 各コミットの関係する比較・型検査が通り、実行できなかった検証が明記されている。
- 既知の不具合を構造変更に混ぜて修正していない。
- 計算量の改善を行った場合は、別コミットと同等性・改善の証拠がある。
- ローカルコミットの一覧と変更点を報告し、pushしていない。

旧 `main.py` への接続、旧実装の削除、残りの旧手法の移植は、この計画の完了条件に含めない。
